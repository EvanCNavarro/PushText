# Task 11 - SPIKE: does `start(inputSequence:)` work on this Tahoe build?

**Verdict: GO.** `SpeechAnalyzer.start(inputSequence:)` does not reproduce FB22149971 on this
machine. #12 is a straightforward `TranscriptionEngine` conformer against the streaming path, not a
pivot to chunked file transcription.

Measured 2026-08-22, immediately after the toolchain moved.

| | |
|---|---|
| macOS | 26.6.2 (25G83) - read from `ProcessInfo.operatingSystemVersion` inside the spike |
| Xcode | 26.6, build 17F113 |
| SDK | `macosx26.5` |
| Swift | 6.3.3, target `arm64-apple-macosx26.0` |

The radar was filed against macOS **26.3**. This machine is six point releases later, which is the
most likely explanation for the difference - but that is an inference, and this document does not
claim it. What was executed is below.

---

## 1. What was actually run

A standalone SwiftPM executable, preserved at `docs/verification/spikes/11-streaming/`, with three
arms over identical audio:

- `env` - environment and model inventory, no audio
- `batch` - `analyzer.analyzeSequence(_:)` (the control)
- `streaming` - `analyzer.start(inputSequence:)` (**the call under test**)

Both transcription arms use the same locale, the same `SpeechTranscriber` preset
(`.progressiveTranscription`), the same PCM buffers and the same chunk size. **The only difference
between them is the entry point.** That is what makes a streaming-specific failure distinguishable
from a broken setup.

Audio is a fixed 6.48 s WAV generated by `say` with known ground truth, so the input is identical
across every run:

```
say -o sample.wav --data-format=LEF32@48000 \
  "The quick brown fox jumps over the lazy dog. Push text turns speech into text on device."
```

Buffer start times are derived from a running frame count, so they are monotonic and contiguous by
construction - the same property `AudioRingBuffer` guarantees. This deliberately excludes the third
of the radar's three suspected causes before the test begins.

run twice each:

```

frames=1024 run=1 streaming_ok=1     frames=1024 run=2 streaming_ok=1
```

10 of 10 succeeded, including both sub-4096 sizes.

## 5. The green was battle-tested before it was believed

A verdict line that has never printed a failure is a rumour. Two failures were planted.

**Plant A - missing audio file.** Proves the `catch` and the error-detail path actually execute:

```
VERDICT=STREAMING_FAILED swift=Error Domain=com.apple.coreaudio.avfaudio Code=2003334207
  "(null)" UserInfo={failed call=ExtAudioFileOpenURL(...)} | domain=com.apple.coreaudio.avfaudio
  | code=2003334207 | ...
```

**Plant B - deliberately mismatched audio format** (48 kHz fed to an analyzer that chose 16 kHz).
This one did **not** produce a verdict at all:

```
exit=133                       # 128 + 5 = SIGTRAP
```

That is a finding, not a harness defect - see section 6.

Without Plant A, `STREAMING_OK` would rest on never having observed the failure path work. With it,
the verdict is known to be capable of going red for a thrown error.

## 6. What this spike found that it was not looking for

**A format mismatch kills the process rather than throwing** (issue #32). The crash is inside
Apple's own precondition:

```
exception: EXC_BREAKPOINT (SIGTRAP)
crashed thread: com.apple.root.default-qos.cooperative
  Speech  SpeechRecognizerWorker.preRunRecognition()
  Speech  SpeechRecognizerWorker.processAudio(_:for:)
  Speech  closure #1 in SpeechAnalyzer.processInput(_:)
```

`bestAvailableAudioFormat` chose **16 kHz mono**; `AVAudioEngineCapture` delivers the device's
native **48 kHz**. Those differ by default, so #12 must convert rather than forward. No `catch` can
save it. See TRAP-20.

**Apple Intelligence is not ready on this machine** (issue #33). The crash report carried
`"appleIntelligenceStatus" : {"state":"restricted","reasons":["assetIsNotReady"]}`, which is a
`FoundationModels` (#14) input, not a Speech one.

**The WWDC-era API names are gone.** Checked against the shipping interface, not the docs:
`allocatedLocales`, `deallocate(locale:)` and `.offlineTranscription` appear **0** times in
`Speech.swiftinterface`. `reservedLocales`, `release(reservedLocale:)` and `.transcription` are what
exist. The signature under test is:

```swift
final public func start<InputSequence>(inputSequence: InputSequence) async throws
  where InputSequence: Sendable, InputSequence: AsyncSequence,
        InputSequence.Element == Speech.AnalyzerInput
```

## 7. What this does NOT establish

- **Nothing about the real microphone path.** Every run above is file-fed. The API question is
  answered; whether `AVAudioEngineCapture`'s live buffers drive the analyzer correctly is #12's
  work, and #32 is the specific hazard on that seam.
- **Nothing about transcription quality.** Ground truth was "The quick brown fox jumps over the lazy
  dog. Push text turns speech into text on device."; both arms returned "went around the jump over a
  lazy dog. push anditch the head on the device." That is a synthetic `say` voice, which is not what
  the recognizer is tuned for, and accuracy was never what this spike was measuring. Real accuracy
  numbers belong to #15 with a human voice.
- **Nothing about long sessions, silence handling, or cancellation.** 6.48 s of continuous speech
  only.
- **Nothing about the results stream hanging**, which #12's backlog note reports from the field. The
  stream terminated cleanly in all 12 transcription runs here; every await in the spike is
  timeout-wrapped, and no timeout fired.
