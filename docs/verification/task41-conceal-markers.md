# Task 41 - The conceal markers work, and they are load-bearing

**Verified against a real clipboard manager running on the development machine.** Without the
markers, every dictated utterance lands in a searchable clipboard history. With them, none does.

Measured 2026-08-22 on macOS 26.6.2 against **CopyClip 2** (`com.fiplab.clipboard`), which was
already installed and running - not installed for this test.

---

## 1. What was still open

The code half of #41 shipped with the injector: `PasteboardTextInjector.stage` writes ONE
`NSPasteboardItem` carrying the text plus `org.nspasteboard.TransientType`, `ConcealedType` and
`AutoGeneratedType`, and `PasteboardMarkersTests` asserts it - including the subtle part, that the
markers ride on the *same item* as the text rather than a sibling, which a manager would never see.

What had never been done is the thing the issue's TRIGGER actually asked for: *"run a clipboard
manager, dictate, and confirm the utterance does NOT appear in its history."* Unit tests prove we
write the markers. They cannot prove any manager honours them.

## 2. The A/B

`CopyClip` stores its history in a Core Data SQLite file, so "did it archive this?" is a query
rather than a judgement:

```sql
select count(*) from ZCLIPPING where ZCONTENTS like '%<sentinel>%';
```

Both arms write a unique sentinel to `NSPasteboard.general` and hold it for the same dwell. The
**only** difference is the three marker types. The database is copied before each query so the
running app is never disturbed.

**The positive control is the point.** A test that only checks the marked arm cannot tell "the
manager honoured the marker" from "the manager was not watching" - the two produce identical
zeroes. So the unmarked arm has to come back non-zero at the same dwell, or the result means
nothing.

## 3. Results

| arm | dwell | trials | entries in CopyClip history |
|---|---|---|---|
| unmarked (control) | 6 s | 1 | **1** - CopyClip was watching |
| marked | 6 s | 1 | **0** |
| unmarked (control) | **0.12 s** | 3 | **1, 1, 1** |
| marked | **0.12 s** | 3 | **0, 0, 0** |

0.12 s is not an arbitrary second dwell - it is `pasteSettleDelay`, exactly how long production
leaves the item on the pasteboard before restoring the clipboard.

## 4. The markers are load-bearing, not belt-and-braces

The obvious objection to this whole fix is that production holds the pasteboard for only 120 ms, so
a manager polling on a timer might miss the item anyway and the markers would be decoration.

**Measured: it does not miss it.** CopyClip captured the unmarked item on 3 of 3 trials at 120 ms.
Every dictated utterance on this machine would be sitting in a searchable history right now if
`stage` did not set the markers. The research called their absence in OpenSuperWhisper "a privacy
bug" (`docs/research/04` §3.7); on this configuration that is a measurement, not a characterisation.

## 5. What this does NOT establish

- **One manager.** CopyClip honours the convention. Raycast, Maccy, Paste and Alfred are named in
  the issue and were NOT tested - Raycast is installed here but its clipboard history was not
  enabled, and the others are not on this machine. nspasteboard.org is a convention, not an API:
  a manager is free to ignore it, and one that does would archive our text no matter what we set.
- **Not the full injection path.** The arms write to `NSPasteboard.general` directly and send no
  keystroke. What they share with production is the item shape - text plus the three markers on one
  item - which is what a manager reads. The real `stage()` is covered by `PasteboardMarkersTests`
  instead, because exercising it end to end means posting a synthetic Command-V into whatever
  window happens to have focus.
- **Nothing about images or files.** Only `public.utf8-plain-text` was exercised, which is all this
  app ever puts on the pasteboard.
- **A managed history is not deletion.** This keeps text OUT of a third-party archive. It says
  nothing about what macOS itself retains.

## 6. Reproducing

The A/B tool is not committed - it is nine lines around `NSPasteboardItem` and it writes to the
real clipboard, which is not something to leave lying in the repo. Write a sentinel with and
without the three types, hold each for 0.12 s, and query the manager's store. Save and restore the
clipboard around it; both runs above did, verified by comparison afterwards.
